## 1. 背景与问题

1. **面试官管理"意义薄"**：`interviewers` 表只是"教师名册"（姓名/角色/职称），满足任务5 的面试官管理需求，但**数据没有任何下游消费**——面试不归属任何老师、报告不体现面试官、操作不绑定身份。
2. **设计遗留**：`interviews.interviewer_id` 外键从项目初期就存在，但从未被任何接口/前端使用（仅 SQL Agent 白名单提过）。
3. **附带发现**：后台新增企业后，岗位表单的「所属企业」下拉不同步（引用列表只在挂载时加载一次）。

## 2. 方案

采用 **A + B 组合**：
- **A（代码）**：把已存在的 `interviewer_id` 接进面试流程——候选人选岗时可指定本次面试官，对话页与报告展示"AI 面试官：张老师（实习指导教师）"，让名册产生实际业务意义。
- **B（文档）**：明确「面试官表=教师名册=账号体系前身；正式登录鉴权为方案B 后续演进」的答辩口径。
- 不做完整登录（方案C）：三天内做 users 表+鉴权+数据隔离风险过高，半成品登录不如不做。

## 4. 验证结果

- ✅ 全链路：选张老师 → 创建面试（interviewer_id 落库）→ start 返回面试官 → 逐题作答 → 报告含"张老师（实习指导教师）" → 管理员详情 `interviewer_name` 可见

- ✅ 前端 headless：学生端岗位大厅渲染出"选择本次面试官"下拉及"张老师（实习指导教师）"选项
- ✅ 回归：`pytest backend/tests/ -v` → **148 passed**（成员B 接口测试无破坏）
- ✅ 服务带 `--reload` 运行，改动即时生效

## 5. 答辩口径（回答"面试官管理意义/要不要登录"）

> 演示：学生端岗位大厅 → 下拉选张老师 → 开始面试 → 对话页"🎓 AI 面试官：张老师（实习指导教师）" → 报告"本报告由 AI 面试官「张老师（实习指导教师）」根据面试表现自动生成" → 管理员面试记录详情亦可见。
>
> 话术：**面试官名册不只是名单——每场面试现在都有归属**，候选人选岗时指定由哪位老师主持，对话与报告都体现出来。真正的账号登录 + 按教师数据隔离（张老师登录后只能管理自己的面试）为方案B 后续演进，面试官表即账号体系前身。
